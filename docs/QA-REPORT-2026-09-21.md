## 2. Verified as working

Everything below was exercised in this pass and behaved correctly.

### Security (audit SEC-01 / SEC-02 / SEC-03 — all three closed)

* **Nothing renders without a verified session.** `curl` of every route while signed out (local and
  live): `/revnu`, `/developer?dev=…`, `/sales?dev=…&order=…`, RSC payloads, and every JavaScript
  chunk served to the sign-in page — no "grovadevelopments", no "CR 7050932065", no commission
  percentages, no unit prices. `/`, `/login` and `/login?dev=…` carry only brand chrome.
* **Sessions cannot be forged.** A hand-built cookie, and a real token with a tampered payload
  (`sub` swapped for the super admin's id), are both rejected — the server validates the JWT with
  Supabase Auth, and the same token is refused by the database. After a global sign-out the refresh
  token is dead.
* **Portal rules hold.** A rep cannot open `/revnu`; Revnu staff cannot open `/developer` or run the
  sales wizard (they may only open a recorded agreement read-only); `?dev=<other tenant>` always
  bounces to the person's own home. Verified for all three roles across 14 deep links.
* **Every write the UI never offers is refused by the database.** ~230 direct INSERT / UPDATE /
  DELETE attempts as a sales rep across all 30 tables; every RPC with another tenant's order id;
  `attach_document` with a path outside the order's folder and with `..` traversal; storage
  upload / download / `createSignedUrl` across tenants; profile self-escalation (perms,
  `revnu_role_id`, `developer_id`, role, commission level, e-mail, `deleted_at`); reactivating a
  removed colleague; `/api/users` and `/api/users/:id/reset-password` as a rep or as another
  tenant's admin. All refused.
* **Tenant isolation, both directions, proved on a real second tenant.** A second developer was
  onboarded through Revnu HQ → *Onboard developer* (brand, logo, admin account, commission ladder,
  project, unit type, unit). Its admin sees only its own data — store contents: 1 developer, 0 of
  Noor Khuzam's units, orders, profiles, documents, tickets or leads — and cannot read or write
  anything of Noor Khuzam's through the API or Storage. Noor Khuzam's director cannot see the new
  tenant at all. The tenant was deleted afterwards.
* **Money permissions.** Developer-side finance and directors cannot mark a Revnu receivable paid
  (audit B-08 — the developer portal is read-only for these); a Revnu *Admin* can tick a milestone
  but only a **Super Admin** can un-tick one; only Revnu `financials` can attach a transfer proof.
* **`/api/notifications/dispatch`:** POST is 401 signed out and works for any signed-in user (it
  only touches queued rows, by design); GET is 403 without a secret, with a wrong secret, and with
  a wrong bearer token.

### Order lifecycle

* **One unit, one live deal (B-01).** Two reps in two browsers submitting the same unit at the same
  moment: exactly one order is created, the loser sees "Unit 14094-A-5-1-201 was just taken by
  another deal. Please choose a different unit." (Arabic equivalent in an Arabic session) and is
  returned to the unit step; exactly one live `order_units` row remains.
* **Gates hold from every surface** — developer table shortcut, developer drawer, rep kanban, Revnu
  HQ drawer, and `transition_order` called directly — including after re-enabling a disabled button
  in the DOM. "Signed" without a signed contract and "Paid" without a proof of payment are refused
  every time, and steps cannot be skipped.
* **Uploads (B-06).** A 26 MB file → "That file is too large. The limit is 25 MB."; `.exe` and
  `.zip` → "That file type isn't supported."; network killed mid-upload → "You appear to be
  offline."; a cancelled picker does nothing. After every failure: no document row, no Storage
  object, no status change. A successful upload writes exactly one object and one row, and
  **Open signed** / **Open proof** return the real PDF (HTTP 200, `application/pdf`) through a
  10-minute signed URL. Uploading twice keeps both files and uses the latest.
* **Cancel / reinstate / delete.** Cancel demands a reason (empty → "A reason is required.") and
  releases the units; reinstate re-locks them; reinstate after the unit was sold to someone else
  meanwhile is refused with "Cannot reinstate — unit is in another live deal."; a super admin's
  delete releases the units and removes the order everywhere.
* **Order ids never repeat.** Reserved from a monotonic sequence; ids stayed strictly increasing
  across ~60 reservations including deletes (B-03).
* **Invoice and outbox.** Reaching *paid* raises the invoice once and queues the customer e-mail;
  `MAIL_MODE=log` marks it `logged` — **no e-mail left the system during this pass**.

### Accounts and human error handling

Invite from Users & roles → temporary password shown once → sign in as that person in a second
browser → forced password change (under 8 characters and mismatch both refused) → lands in the
right portal for their permissions (a rep gets My deals / My earnings / Inventory and can run the
wizard). Editing permissions takes effect; **Reset password** issues a new temporary password and
forces another change; **Remove** blocks the account immediately (the open session loses all data on
the next request and is bounced to sign-in), hides them from the team list, and **keeps their name
on old orders**. Wrong password, unknown e-mail, a removed account, an expired session mid-action
and the network going down mid-save all produce short bilingual sentences — no stack traces, no
database errors. "Forgot password?" works in log mode: it always reports success without revealing
whether the address exists. The first-run walkthrough runs once per portal and can be replayed; a
support ticket raised in the developer portal appears in Revnu HQ with the sender and page, the
reply is delivered and the status moves open → in progress → resolved.

6th — the counter is per instance and the earlier probes counted; the protection works, the exact
threshold is a one-line constant if the client wants it looser). Leads appear in Revnu HQ →
Interested and their status can be changed and persists.

### Phones (audit R-6 — first real device-size pass)

## 6. Open questions for the client

1. **Tenant-wide order visibility.** Any member of a developer's team can see every order of that
   developer, including colleagues' commission figures, and every team member's IBAN is visible to
   anyone holding the *Team* permission. That mirrors the prototype and was a deliberate decision —
   please confirm it still is, or say whether reps should be limited to their own deals.
2. **Anyone with *Team* can invite a super admin.** A Revnu Super Admin can create another Super
   Admin, and a developer admin with *Team* can grant a colleague every developer permission
   including *Cancel*. Normal for an owner account; confirm that is intended, or we add an approval
   step.
3. **Lead rate limit.** The public form allows 3 submissions per 10 minutes per IP (per server
   instance) before a friendly 429. Is that the threshold you want for a live marketing page?
4. **Receivable milestone ids are not validated.** `set_receivable_paid` accepts a milestone id that
   is not in the developer's terms, and `set_payout_status` accepts a person who is not on that
   order's commission split. Neither is reachable from the UI. Should the server reject them, or is
   the flexibility wanted for one-off corrections?
5. **Uploaded file names are trusted.** A document uploaded as `contract.exe` with a PDF
   content-type is stored (the bucket enforces the declared MIME type, not the extension). It can
   only be opened by people inside that tenant through a signed URL. Do you want the extension
   validated server-side too?
6. **Step strip on phones** (Q-27) — keep the horizontal swipe, or compress the 8 numbers to fit?
7. **Cosmetic React warning** (Q-26) — fix it inside approved styling, or leave it?

## 7. Verdict

**Ship it to staging for client UAT.** The three CRITICAL findings from the audit are genuinely
closed — I could not read a single byte of client data while signed out, could not forge a session,
and could not perform a single write that my role was not allowed, from either the browser or the
API. The order lifecycle is atomic and gated in the database, so the gates hold no matter which
screen (or script) calls them, and the business maths matches the client's own prototype to the
riyal.

The three Blockers I found were real and would have been visible to the client in the first ten
minutes — the sales wizard was unusable as laid out, the commission ladder could not be saved, and
the signed-contract gate could be bypassed through the API. All three are fixed and re-verified.
What is left open is two cosmetic items and a set of decisions that are the client's to make.

One thing must happen before the client can look at any of this: **Vercel has to start building
the project again** (Q-28). Until then the staging URL serves a build from before this pass and is
behind a login wall, so a client opening the link today would see neither the fixes nor, in fact,
the site. That is an account/billing matter, not a code one.

Before going live the cut-over runbook still applies: domain, Resend activation and the SMTP
switch (`docs/CUTOVER.md`), plus handing over the fresh temporary passwords and deleting
